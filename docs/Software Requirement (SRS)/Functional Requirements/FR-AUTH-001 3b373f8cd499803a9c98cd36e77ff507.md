## Overview

This requirement defines the user registration process that allows a customer to create a new Ruma account using a valid email address and password.

After successful registration, the system creates the account in a pending verification state and initiates email verification.

## Description

The system shall provide a registration mechanism that collects the required customer information, validates the submitted data, securely stores the account credentials, creates an email verification token, and sends a verification email.

## Actors

| Actor | Role |
| --- | --- |
| **Customer** | Provides registration information and submits the registration form. |
| **System** | Validates the submitted data, creates the account, creates the verification token, and sends the verification email. |

## Preconditions

- The customer does not have an existing account using the submitted email address.
- The customer can access the registration form.
- The system can access the database.
- The email delivery service is available.

## Trigger

The customer submits the registration form by selecting **Register**.

## Main Flow

1. The customer opens the registration page.
2. The system displays the registration form.
3. The customer provides:
    - Full name
    - Email address
    - Password
    - Password confirmation
4. The customer submits the registration form.
5. The system validates all submitted data.
6. The system verifies that the email address is not already registered.
7. The system hashes the password using Argon2.
8. The system creates a new user account.
9. The system assigns the default role **`CUSTOMER`**.
10. The system assigns the initial account status **`PENDING_VERIFICATION`**.
11. The system creates an email verification token.
12. The system sends the verification email.
13. The system returns a successful registration response.

## Alternative Flow

### A1 — Email Already Registered

- The system detects that the submitted email is already associated with an account.
- Registration is rejected.
- The system returns an appropriate conflict response.

### A2 — Password Confirmation Does Not Match

- The system detects that the password and confirmation password are different.
- Registration is rejected.
- The system returns a validation error.

### A3 — Invalid Email Format

- The system detects that the submitted email does not satisfy the required email format.
- Registration is rejected.
- The system returns a validation error.

### A4 — Email Delivery Failure

- The account has already been created successfully.
- The verification token has been created.
- The email delivery operation fails.
- The account remains in `PENDING_VERIFICATION` status.
- The customer can request another verification email through the resend verification flow.

## Postconditions

### If Successful

- A new user account exists.
- The user's password is stored as a secure hash.
- The user's role is `CUSTOMER`.
- The user's account status is `PENDING_VERIFICATION`.
- An email verification token exists.
- A verification email delivery is initiated.

### If Registration Fails

- No new account is created unless the failure occurs after successful account creation during email delivery.
- Invalid registration data is rejected.
- Existing account data is not modified.

## Business Rules

| Rule ID | Rule |
| --- | --- |
| **BR-AUTH-001** | User email addresses must be unique. |
| **BR-AUTH-002** | Passwords must be stored as secure hashes using Argon2. |
| **BR-AUTH-003** | The default role for a newly registered user is `CUSTOMER`. |
| **BR-AUTH-004** | Newly registered accounts must use `PENDING_VERIFICATION` status until email verification is completed. |
| **BR-AUTH-005** | An email verification token must be created after successful account creation. |
| **BR-AUTH-006** | The system must initiate verification email delivery after successful registration. |

## Validation Rules

| Field | Validation |
| --- | --- |
| **Full Name** | Required; 3–100 characters. |
| **Email** | Required; must use a valid email format. |
| **Password** | Required; minimum 8 characters. |
| **Confirm Password** | Must match the password. |

## Acceptance Criteria

- A customer can register successfully using valid registration data.
- An existing email address cannot be registered again.
- Passwords are not stored in plain text.
- Passwords are hashed using Argon2.
- A newly registered account has role `CUSTOMER`.
- A newly registered account has status `PENDING_VERIFICATION`.
- A verification token is created after successful registration.
- A verification email is initiated after successful registration.
- Invalid registration data is rejected.
- Password confirmation mismatch is rejected.
- The registration API returns a successful response when registration succeeds.

## Notes

- Passwords must never be returned through the API or email.
- Password hashing uses Argon2.
- Verification tokens are temporary credentials and must be securely stored.
- Email verification is required before the account can become `ACTIVE`.
- The exact verification token lifetime is configurable according to the authentication policy.
