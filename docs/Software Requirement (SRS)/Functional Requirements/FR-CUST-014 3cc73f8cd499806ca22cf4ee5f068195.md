## Overview

This requirement defines the process that allows an authenticated customer to request cancellation of an order belonging to their account.

Order cancellation is subject to the applicable order status and cancellation rules defined by the Order module.

## Description

The system shall allow an authenticated customer to cancel an eligible order belonging to their account.

The system shall verify the customer's authentication session and order ownership before processing a cancellation request.

The system shall determine whether the selected order is eligible for cancellation according to the configured order lifecycle and cancellation rules.

The system shall update the order state only when the cancellation request is valid and successfully processed.

## Actors

| Actor Role | Description |
| --- | --- |
| **Customer** | Requests cancellation of an eligible order. |
| **System** | Authenticates the customer, verifies order ownership and cancellation eligibility, processes the cancellation, and returns the result. |
| **Order Management** | Maintains the order lifecycle and determines the resulting order state. |
| **Payment Service** | May be involved where cancellation affects an existing payment according to the implemented payment policy. |

## Preconditions

- The customer has an existing account.
- The customer is authenticated.
- The authentication session is valid.
- The associated customer account exists.
- The selected order exists.
- The selected order belongs to the authenticated customer.
- The selected order is in a state that allows cancellation.
- The system can access the order data.

## Trigger

The customer selects **Cancel Order** for an eligible order and confirms the cancellation request.

## Main Flow

1. The customer opens **Order History**.
2. The customer selects an order.
3. The system displays the order information and available actions.
4. The customer selects **Cancel Order**.
5. The system verifies the customer's authentication session.
6. The system verifies that the order belongs to the authenticated customer.
7. The system verifies that the current order status permits cancellation.
8. The system processes the cancellation request.
9. The system updates the order state according to the configured cancellation policy.
10. The system handles any related payment or operational state according to the applicable business rules.
11. The system returns a successful cancellation response.
12. The updated order status is displayed to the customer.

## Alternative Flow

### A1 — Authentication Required

- The customer does not have a valid authentication session.
- The system rejects the cancellation request.
- The order is not modified.

### A2 — Order Not Found

- The selected order does not exist.
- The system rejects the request.
- The order is not modified.

### A3 — Order Does Not Belong to Customer

- The selected order belongs to another customer.
- The system rejects the request.
- The order is not modified.
- The system does not expose the other customer's order information.

### A4 — Order Not Eligible for Cancellation

- The selected order is in a state that does not permit customer cancellation.
- The system rejects the cancellation request.
- The order remains in its current state.
- The system informs the customer that the order cannot be cancelled.

### A5 — Cancellation Already Processed

- The order has already been cancelled or has reached a terminal state.
- The system does not perform a duplicate cancellation.
- The system returns an appropriate response indicating the current state.

### A6 — Cancellation Processing Failure

- The system cannot complete the cancellation operation.
- The system returns an appropriate error.
- The order remains unchanged unless a transactional policy explicitly defines a partial state.

### A7 — Related Payment Processing Failure

- Order cancellation requires related payment-state processing.
- The payment operation fails or cannot be completed.
- The system handles the failure according to the configured payment and cancellation policy.
- The order must not be incorrectly represented as fully cancelled when the required cancellation transaction has not successfully completed.

## Postconditions

### If Successful

- The eligible order is cancelled according to the configured order lifecycle.
- The customer can see the updated order status.
- Related operational and payment states are updated according to the applicable policy.

### If Failed

- The order remains unchanged unless a defined transactional policy explicitly specifies otherwise.
- No unrelated customer order is modified.

## Business Rules

| Rule ID | Rule |
| --- | --- |
| **BR-CUST-068** | Only an authenticated customer can request cancellation of an order. |
| **BR-CUST-069** | A customer can only cancel orders belonging to their own account. |
| **BR-CUST-070** | An order can only be cancelled when its current state permits cancellation. |
| **BR-CUST-071** | Order ownership and cancellation eligibility must be verified server-side. |
| **BR-CUST-072** | A cancelled order must transition to the appropriate cancellation state defined by the Order module. |
| **BR-CUST-073** | A cancellation operation must not modify unrelated customer orders. |
| **BR-CUST-074** | Related payment handling must follow the configured payment and cancellation policy. |

## Validation Rules

| Field | Validation |
| --- | --- |
| **Authentication Session** | Must be valid and associated with an existing customer. |
| **Order Identity** | Must reference an existing order. |
| **Order Ownership** | The order must belong to the authenticated customer. |
| **Order Status** | Must be eligible for customer cancellation. |
| **Cancellation Request** | Must represent a valid cancellation action. |

## Acceptance Criteria

- An authenticated customer can request cancellation of an eligible order.
- An unauthenticated customer cannot cancel an order.
- A customer cannot cancel another customer's order.
- An ineligible order cannot be cancelled.
- A successfully cancelled order displays the correct cancellation status.
- Duplicate cancellation does not produce an unintended state change.
- A failed cancellation does not incorrectly mark the order as cancelled.
- Related payment handling follows the configured cancellation policy.
- Cancellation does not modify unrelated orders.

## Notes

- Customer cancellation is limited by the order lifecycle and cancellation eligibility rules.
- The exact cancellable order statuses are to be defined by the Order module.
- Payment consequences of cancellation depend on the implemented Payment module and applicable transaction rules.
- Order cancellation should be processed consistently with the overall order lifecycle defined in the PRD.
- Return/refund management is explicitly outside the v1.0 scope, so this requirement does not define a customer return/refund workflow.
